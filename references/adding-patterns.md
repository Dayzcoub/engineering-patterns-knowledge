# Как добавлять паттерны

1. Внести источник в `data/sources.json` (URL, дата проверки/статус и автор при необходимости).
2. Добавить карточку с новым стабильным kebab-case ID в `data/patterns.json`.
3. Карточка должна содержать: симптомы, когда применять, подход, когда НЕ применять, проверку, источник, проекты и приоритет.
4. Для документов с ограниченными правами использовать собственные краткие описания и прямые ссылки; не архивировать чужие книги/статьи без лицензии.
5. Сначала помечать `index_only`, потом `reviewed` после чтения, `pending_primary_review` для временно недоступных материалов. Не считать обзор поискового результата полным чтением.
6. Добавить unit/contract/physical verification guidance, если паттерн касается аудио, безопасности, восстановления или IPC.
7. Прогнать `python scripts/validate.py`; проверить поиск по русским/английским ключам.
8. Повысить priority только при конкретной потребности в проекте. Раз в квартал проверять битые ссылки и устаревшие API.
9. Сохранять changelog и версию. Source commit источника фиксировать при полном повторном импорте.
10. Любая интеграция в production должна проходить отдельный PR с тестами; обновление скилла само по себе не меняет код.

11. Для real-time audio отделять проверенные контракты API от локальной политики измерений: статус `reviewed` относится только к первоисточникам, а не к физическому тесту. Сохранять requested/effective frames и конфигурацию устройства отдельно.

12. Для WPF указывать, проверен ли конкретный runtime/OS/DPI-awareness; общий Microsoft источник не является доказательством UI PASS в KLIDAN.

13. Для SQLite разграничивать crash atomicity, power-loss durability, WAL-sidecar и операции вне БД. Протокол multi-store reconciliation не считать гарантией SQLite без независимых fault-injection тестов.
14. Для STAYA различать process, listener, public subscription route, admin API и transport/egress. Для каждой проверки писать scope и доказательство.
15. В QA-сценариях и документации использовать только synthetic credentials; production URL подписок с токенами не копировать в Git.
16. Update-паттерны обязаны указывать signer trust, artifact digest provenance и способ защиты от старых метаданных. MSI-specific решения нельзя автоматически применять к другому установщику.
17. Telemetry-паттерны должны иметь ограничения cardinality и явную обработку секретов; stage journal не доказывает успешное подключение к сети.
